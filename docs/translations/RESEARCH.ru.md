# Конвертация карт Counter-Strike 1.6 → Killing Floor 1

[English](../RESEARCH.md) · **Русский**

Исследование выполнимости автоматической конвертации GoldSrc BSP v30 → Unreal Engine 2.5 `.rom`
(геометрия, освещение, текстуры, коллизия, модели), 2026-08-06.

---

> **Статус: реализовано.** Маршрут C (прямая запись `.rom`) написан и работает — код в корне
> репозитория. `node src/cli.js <map.bsp> --out <Maps> --verify`. Покрытие граней на тестовых картах
> 98.5–99.6 %, сериализатор `UModel` проверен байт-в-байт на 41 стоковой карте KF, готовые карты
> грузятся движком без единого `Critical`. Открытые пункты (коллизия, небо, пути ботов) перечислены
> в [README](../../README.md).

## 0. Вердикт

**Возможно. Полностью автоматический конвертер реализуем.** Главный блокер, который считался
нерешаемым (формат запечённого освещения BSP в `UModel` v128), в ходе этого исследования **вскрыт и
провалидирован на 362 картах из 362**.

Три архитектуры, от дешёвой к правильной:

| # | Маршрут | Освещение | Автоматизация | Трудоёмкость | Риск |
|---|---|---|---|---|---|
| A | BSP → `.t3d` браши → KFEd → Build | пересвет заново | ручной шаг в GUI | 1–2 нед | высокий (CSG давится) |
| **B** | **BSP → тесселированный StaticMesh (`.ase`) + лайтмап в vertex colors → KFEd import** | **перенос ~1:1 через цвета вершин** | **1 ручной шаг** | **3–5 дней** | **низкий (28 рабочих карт-прецедентов)** |
| C | BSP → прямая запись `.rom` (свой сериализатор UE2.5) | перенос 1:1 в DXT3-атласы | полная | 3–6 нед | средний |

**Рекомендация: начать с B, при необходимости эволюционировать в C.** B даёт рабочий результат за
несколько дней и опирается на путь, которым уже сделаны 28 живых карт `KF-CS-*` на ваших серверах.
C — «правильная» цель: единственный маршрут, дающий настоящие BSP-лайтмапы, зоны, порталы и
LeafHull-коллизию, и он больше не заблокирован.

Ни один маршрут не даёт карту, готовую к игре «из коробки»: пути ботов (`PathNode` + `ReachSpec`),
торговец и зомби-волюмы придётся строить отдельно (в KFEd операцией `PATHS BUILD` либо своим
генератором).

## 1. Что измерено (собственные замеры, не литература)

### 1.1 Сторона CS 1.6

Парсер BSP30 написан заново, проверка — расчётный объём лайтмапов обязан совпасть с лампой
`LUMP_LIGHTING`:

| карта | faces | освещ. faces | лайтмап-лампа | текстуры | brush-модели |
|---|---|---|---|---|---|
| de_dust | 5550 | 4482 | 551 КБ | 30 (все из WAD) | 48 |
| de_dust2 | 5383 | 4002 | 491 КБ | 44 (15 встроено) | 43 |
| cs_office | 9384 | 8390 | 754 КБ | 214 (101 встроено) | 206 |
| de_inferno | 9347 | 8587 | 1173 КБ | 97 (все встроены) | 155 |
| cs_italy | 8528 | 7839 | 1014 КБ | 102 (все из WAD) | 102 |

Расчёт `w = extents[0]/16 + 1`, `h = extents[1]/16 + 1`, `bytes = w*h*3*styles` даёт суммарно
**4050 КБ против 3983 КБ фактических — коэффициент 1.017**. Формула сетки люкселей подтверждена.
Многослойных (мигающих) лайтстайлов в этих пяти картах нет вообще — перенос однослойный.

Спецтекстуры, которые встречаются и требуют отдельной обработки: `sky`, `{name` (маска, прозрачен
индекс палитры 255), `~name` (излучатель), `+0name` (анимация), `-0name` (случайный тайлинг),
`aaatrigger`, `hint`, `origin`.

Критично: **вершины brush-энтити хранятся в системе координат энтити**, мировая позиция =
`vertex + entity.origin` (hlcsg вычитает origin-браш при компиляции). `dmodel_t.origin` при этом
нулевой, полагаться на него нельзя.

### 1.2 Сторона Killing Floor — формат `UModel` v128 вскрыт

Порядок сериализации (ветка `Ver >= 110`), проверен на **362 картах из 362 — точное попадание в
`serialSize` до байта**:

```
[UObject props "None"] [FBox 25] [FSphere 16]
Vectors  TArray<FVector>
Points   TArray<FVector>
Nodes    TArray<FBspNode>     // v128: канон + ExclusiveSphereBound + iSection,iFirstVertex,iLightMap
Surfs    TArray<FBspSurf>     // v128: ... + Plane(16) + LightMapScale(float, обычно 32.0)
Verts    TArray<FVert>
INT NumSharedSides
INT NumZones ; FZoneProperties Zones[NumZones]   // {cidx ZoneActor, QWORD Conn, QWORD Vis, FLOAT}
cidx Polys
TArray<FBox>  Bounds          // 25 Б на элемент
TArray<INT>   LeafHulls
TArray<FLeaf> Leaves          // {cidx iZone, cidx iPermeating, cidx iVolumetric, QWORD VisibleZones}
TArray<AActor*> Lights        // cidx на элемент
INT RootOutside ; INT Linked
TArray<FBspSection>     Sections       // FBspVertexStream(40 Б/верт) + Material + NumNodes + PolyFlags + iLightMapTexture
TArray<FLightMap>       LightMaps      // 7×cidx + FMatrix(64) + 3×FVector(36) + TArray<FLightBitmap> + cidx Level + INT Rev
TArray<FLightMapTexture> LightMapTextures
```

Именно неверное предположение о порядке (ожидались `LightMap`/`LightBits` сразу после `Polys`, как
в UE1) раньше ломало разбор. В UE2.5 `FLightMapIndex`/`LightBits` — мёртвая ветка `Ver < 105`.

**Как выглядит освещение BSP в KF:**

| карта | геометрия | трейлер | LightMaps | shadow-битмапы | атласы |
|---|---|---|---|---|---|
| Entry.rom | 1 КБ | 321 КБ | 0 | 0 | 1 × DXT3 512×512 (320 КБ) |
| KF-CS-Action | 66 КБ | 764 КБ | 294 | 103 (1 КБ) | 2 × DXT3 512×512 (640 КБ) |
| KF-BioticsLab | 437 КБ | 5546 КБ | 1221 | 8911 (1656 КБ) | 9 × DXT3 512×512 (2880 КБ) |

То есть: **запечённый RGB-лайтмап в DXT3-атласах 512×512 (2 мипа, 320 КБ на атлас) прямо внутри
объекта `Model`**, плюс по одному 1-битному теневому битмапу на каждый влияющий источник (для
пересчёта переключаемого света в рантайме). Геометрия — 8–13 % объёма карты, остальное — свет.

**Это формат-совместимо с GoldSrc**: там тоже запечённый RGB. Перенос освещения 1:1 принципиально
возможен, чего до сих пор никто не делал (прецедентов инъекции лайтмапа в UE2.x не найдено).

### 1.3 Масштаб — измерен по рабочему порту

`cs_estate.bsp`: мир 3016 × 3232 × 672 HL-юнита.
`KF-CS-Estate-KFN.rom`, меш `csestate`: локально 2832 × 2976 × 616 при **DrawScale = 2.0**.

**Портеры использовали ×2.** Побочный эффект, который стоит понимать: сетка люкселей HL — 16 юнитов;
×2 = 32 UU = ровно дефолтный `LightMapScale` в UE2.5. При масштабе 2 люксели GoldSrc ложатся на
лайтмап-сетку Unreal **один в один, без ресемплинга**.

Пропорционально «правильный» масштаб другой: игрок HL 32×32×72, KF `KFHumanPawn` — радиус 20,
полувысота 50 (100 UU). По росту это ×1.39. При ×2 игрок относительно геометрии на 44 % мельче, чем
в CS — двери и коридоры становятся просторнее. Для KF (6 игроков + толпа зедов) это скорее плюс, и
именно так сделаны живые карты. Расхождение осознанное, не ошибка.

Что ломается при ×2 и требует ручной правки:
- прыжок: `JumpZ=325` при гравитации −950 даёт ≈55.6 UU, уступ HL 45 ю → 90 UU — непреодолим;
- вентиляции: HL 37 ю → 74 UU против 68 UU присевшего KF-игрока — на грани;
- ступени: `MAXSTEPHEIGHT = 35.0` (константа `Actor.uc`, не свойство) — препятствия 9–17 HL-юнитов
  перестают быть препятствиями.

### 1.4 Прецеденты: как реально сделаны 35 карт `KF-CS-*`

Разбор их пакетов даёт две чётко различимые школы:

**Школа A — автоматический импорт BSP→меш (28 карт).** Весь уровень — один `StaticMesh`, названный
по исходному файлу GoldSrc-карты (`gg_2House`, `aim_map_glock`, `x_hero_siege`, `csestate`,
`Iceworld`…). BSP схлопнут до 3–30 брашей — это только оболочка зоны и комната торговца. Текстуры
названы `<исходноеимя>_material_N` и имеют исходные размеры WAD-текстур. Проверено мной на
`KF-CS-Iceworld`: 15 `StaticMesh` (907 КБ), BSP всего 78 surfs, 14 `Light`, 75 `StaticMeshInstance`.

**Школа B — ручная сборка в UnrealEd (7 карт).** `KF-CS-Dust`: 718 брашей, 651 КБ `Polys`, 17 КБ
мешей. `KF-CS-Office`: 559 брашей + 1196 `StaticMeshActor` из **стоковых** ассетов KF. Автор Office
пишет «I recreated cs_office» — это ремейк, не конвертация.

Опубликованного инструмента или туториала «GoldSrc → Unreal» не существует. Инструмент, породивший
`<map>_material_N`, нигде не назван; нейминг характерен для цепочки OBJ/FBX → 3D-пакет → ASE.

### 1.5 Автоматизация KFEd — что есть и что не работает

В SDK (`killingfloor-sdk-nonsteam`) присутствуют `KFEd.exe`, `UCC.exe`, `Editor.dll` c экспортёрами
T3D (`ULevelExporterT3D`, `UPolysExporterT3D`, `UStaticMeshExporterT3D`), фабриками импорта
(`ULevelFactory`, `UPolysFactory`, `UStaticMeshFactory`) и полным набором токенов ASE-парсера,
включая `*MESH_CVERTLIST` / `*MESH_VERTCOL` — **цвета вершин через ASE импортируются**.

`ucc rebuild` существует (`Syntax: ucc rebuild <file[s]>`), но **проверен и непригоден**:

| вход | выход |
|---|---|
| `Entry.rom` 335 882 Б | пакет **64 байта** (пустой) |
| `KF-CS-Action` 399 nodes / 2 атласа / 294 LightMaps | **6 nodes / 0 атласов / 0 LightMaps** |

Строку `Rebuilding...` он не печатает ни разу — только `Loading…/Saving…/Cleaning up…`.
Он пересобирает мир из исходных CSG-брашей и уничтожает всё построенное, освещение не строит
вообще. Как шаг конвейера использовать нельзя.

Ключа `-EXEC=` у UT2004/KF нет. Импорт T3D задокументирован только как интерактивная операция
редактора. **Полностью headless-сборки карты штатными средствами не существует.**

## 2. Соответствие форматов

| Сущность | GoldSrc BSP30 | UE2.5 v128 | Перенос |
|---|---|---|---|
| вершины | `LUMP_VERTEXES` float×3 | `Model.Points` | прямой, ×масштаб |
| плоскости | `dplane_t` | `FBspNode.Plane` + `Model.Vectors` | прямой |
| дерево | `dnode_t.children[2]`, отриц. = лист | `iBack`/`iFront`, копланары через `iPlane` | k граней узла → 1 узел + k−1 копланарных |
| грань | `dface_t` + `surfedges`→`edges` | узел с `NumVertices` + `Verts[iVertPool…]` | прямой, обход рёбер со знаком |
| UV | `texinfo.vecs[2][4]`, в текселях | `pBase` + `vTextureU/V`, тексели/юнит | прямой; `Origin = pBase`, оси делятся на масштаб |
| текстура | miptex 8-бит + палитра 256 | `UTexture` P8+`UPalette` либо DXT | P8 переносится без перекодирования |
| маска | `{name`, прозрачен индекс 255 | `PF_Masked`, прозрачен индекс **0** | переставить палитру |
| небо | текстура `sky`, `TEX_SPECIAL` | `PF_FakeBackdrop` + `SkyZoneInfo` + куб неба | прямой |
| освещение | RGB24, 16 ю/люксель | DXT3-атлас 512×512, `LightMapScale` 32 UU | при ×2 — 1:1 |
| коллизия | clipnodes, 3 раздутых халла | `LeafHulls` + `iCollisionBound`, движок раздувает сам | халлы CS не нужны, строится из hull 0 |
| зоны/PVS | `LUMP_VISIBILITY`, листья | `Zones[64]`, `FLeaf.VisibleZones`, `Connectivity` | leaf→zone кластеризация, максимум 64 |
| brush-энтити | submodel `*N` + `origin` | отдельный `Model`+`Polys` на волюм / `Mover` | func_wall→геометрия, func_door→`Mover` |
| статичные модели | `cycler`/`monster_furniture` → `.mdl` v10 | `StaticMesh` | mdldec → SMD → ASE |
| спрайты | `.spr` v2 | `Texture` + `SpriteEmitter` | прямой |
| свет-энтити | `light`, `light_spot`, `light_environment` | `Light`, `Spotlight`, `Sunlight` | прямой, яркость подбором |

Безвозвратно потеряно ещё в BSP (не наша вина, восстановлению не подлежит): исходные браши,
tool-браши `CLIP`/`NULL`/`HINT`, точное положение brush-энтити (origin округлён до целых), исходное
разбиение стен на грани.

## 3. Рекомендуемая архитектура (маршрут B)

Один Node-конвертер, шесть стадий. Стадии 1–5 полностью автоматические, стадия 6 — один проход в
KFEd.

**1. Чтение BSP.** Лампы, грани через `surfedges`, UV из `texinfo`, лайтмапы по `lightofs`,
submodels + `origin` энтити, список WAD из `worldspawn.wad`. Уже написано и провалидировано
(см. §1.1).

**2. Текстуры.** Встроенные miptex + внешние WAD3. Спецпрефиксы: `sky` — вырезать грани и заменить
кубом неба; `{` — переставить палитру так, чтобы прозрачный индекс стал 0, флаг `bMasked`; `+0` —
взять кадр 0; `~` — пометить для стадии 5. Пишутся в `.utx` (P8 + `UPalette`, без перекодирования)
или в ASE как ссылки на BMP.

**3. Геометрия + тесселяция под свет.** Грани группируются по текстуре, каждая режется по сетке
люкселей 16 ю. В каждую вершину пишется цвет из лайтмапа GoldSrc (билинейно). Порядок ~186 тыс.
вершин на de_dust — режется на куски по 65 тыс. (лимит 16-битного индекса `IndexStream1`).

**4. Экспорт ASE.** `*GEOMOBJECT` на кусок, `*MATERIAL_LIST` с сабматериалами, `*MESH_MTLID` на
треугольник, `*MESH_TVERTLIST` — диффузные UV, `*MESH_CVERTLIST`/`*MESH_VERTCOL` — запечённый свет.

**5. Скелет карты в `.t3d`.** Оболочка мира (один вычитаемый куб) + куб неба + `SkyZoneInfo` +
`ZoneInfo` + `PlayerStart` из `info_player_*` + `Light`/`Spotlight`/`Sunlight` из светоэнтити (для
динамики: фонарик, вспышки выстрелов) + `Mover` из `func_door`.

**6. Сборка в KFEd (ручная, ~10 минут).** Импорт ASE в `.usx` → импорт `.t3d` → расстановка мешей →
`Build Geometry` → `Build Paths` → сохранить `.rom`.

### Что проверить до начала (единственная неподтверждённая посылка B)

Использует ли UE2.5 `UStaticMesh.ColorStream` для освещения меша, или свет берётся только из
`UStaticMeshInstance.ColorStream`, который строит редактор. Если верно второе — цвета из ASE будут
затёрты при `Build Lighting`, и стадию 3 придётся заменить на генерацию `StaticMeshInstance`
(структура простая: `TArray<FStaticMeshLightInfo> Lights` + `FRawColorStream`), либо просто
принять свет от расставленных `Light`-актёров.

**Проверка на 20 минут:** собрать в KFEd куб с вершинными цветами из ASE, построить свет, выгрузить
`.rom`, сравнить `ColorStream` меша и `StaticMeshInstance` моим парсером.

## 4. Маршрут C — прямая запись `.rom`

Теперь реализуем, потому что формат целиком известен. Что нужно написать:

1. **Сериализатор пакета UE2.5** — таблицы имён/импортов/экспортов, compact index, GUID, смещения.
   Готовых open-source писателей для v128 нет ни одного; ближайшее — `EliotVU/Unreal-Library` (MIT,
   уже читает KF-пакеты, есть половина записи заголовка). Читатель у вас уже есть — запись
   симметрична.
2. **Трансляция дерева** GoldSrc → `FBspNode`, дедупликация `Points`/`Vectors`, `Surfs`, `Verts`.
3. **`LeafHulls`** — плоский `TArray<INT>` индексов узлов, бит `0x40000000` = «взять плоскость
   инвертированной», `-1` = конец халла; `FBspNode.iCollisionBound` указывает на начало. **Самое
   рискованное место**: без него объёмные трассировки не находят примитив и игроки проваливаются
   сквозь мир, при том что хитскан продолжает работать (то есть баг не заметен на первый взгляд).
4. **`Sections`** — батчи рендера, `FBspVertex` 40 Б (позиция, UV, UV2-лайтмап, нормаль).
5. **`LightMaps` + атласы** — упаковка люкселей GoldSrc в DXT3 512×512, матрицы `WorldToLightMap`,
   `LightMapBase/X/Y`. При масштабе ×2 ресемплинг не нужен.
6. **`Zones`** — кластеризация листьев ≤64 зон, `Connectivity`/`Visibility` из PVS GoldSrc.
7. **Актёры** — `Level` (`Actors[]` + ссылка на `Model`), `LevelInfo`, `LevelSummary`, `ZoneInfo`,
   `PlayerStart`.

Исходные `Brush`/`Polys` не нужны: объекты с флагами `NotForClient|NotForServer` движок пропускает
целиком (это ровно то, на чём стоит ваш `kfmapguard`). Исключение — волюмы: каждому нужен свой
`Model` + `Polys` с игровыми флагами.

Пути ботов остаются вне охвата и здесь: либо один проход `PATHS BUILD` в KFEd, либо свой генератор
`PathNode` + `ReachSpec` (данных достаточно — есть и геометрия, и коллизия).

## 5. Правовая рамка

Валв разрешает перенос ассетов между играми в некоммерческих модах, но отдельно оговаривает, что
**«vanilla maps should generally not be ported verbatim»**. Tripwire требует, чтобы моды не содержали
чужой защищённой собственности без письменного разрешения и распространялись бесплатно. Оба
найденных публичных KF-порта CS-карт (`KF-Dust_1`, `KF-Assault`) удалены из Steam Workshop за
нарушение правил. Кастомные CS-карты (`gg_iceworld`, `x_hero_siege`, `fy_*`) принадлежат их авторам,
а не Valve — разрешение нужно у них.

Практический вывод: на своих серверах риск такой же, как у уже стоящих 35 карт `KF-CS-*`; публикация
в Workshop — нет.

## 6. Что осталось непроверенным

- Источник освещения статических мешей (`UStaticMesh.ColorStream` против
  `UStaticMeshInstance.ColorStream`) — блокирует выбор внутри маршрута B, проверяется за 20 минут.
- Точное поведение `FLightMap.WorldToLightMap` / `LightMapBase/X/Y` — поля прочитаны и размеры
  сходятся на 362 картах, но семантика (как именно строится лайтмап-UV) не декодирована.
- Формат `FStaticLightMapTexture.Format`: измерено DXT3 на всех проверенных картах, но конфиг
  `UseCompressedLightmaps` допускает и RGBA8 — писатель должен поддержать оба.
- Ограничение UnrealEd на браши >500 граней (известно по документации `bsp2t3d`) не проверялось на
  KFEd — существенно только для маршрута A.
- Проходит ли `#exec MAP IMPORT FILE=` под `ucc make` — единственный непроверенный шанс убрать
  ручной шаг из маршрута B. `ucc make` молча игнорирует неизвестные `#exec`, так что проверять надо
  по факту появления файла, а не по коду возврата.

## Приложение: инструменты для повторения замеров

`scripts/`, каждый — на голом Node без зависимостей:

| файл | что делает |
|---|---|
| `bspstat.js` | парсер BSP30: лампы, грани, расчёт лайтмап-сетки (самопроверка: расчёт против размера лампы), энтити, спецтекстуры, bbox мира |
| `umodel-trailer.js` | полный парсер `UModel` v128 включая трейлер; оракул — точное попадание в `serialSize` |
| `romstat.js` | инвентарь `.rom`: классы экспортов, мир-`Model`, статические меши, текстуры, актёры |
| `meshbbox.js` | габариты уровневого меша × `DrawScale` — измерение масштаба порта |
| `smallest.js` | ранжирование карт по размеру трейлера — так была найдена `Entry.rom` для ручного разбора |
| `probe.js`, `entry.js` | побайтовые пробы трейлера (использовались при вскрытии формата) |
| `strings.js` | ASCII-строки из `Editor.dll`/`Engine.dll` — так найдены коммандлеты и токены ASE |

Читатель пакетов — `kfrom.js` из
[killingfloor-map-viewer](https://github.com/TheBestPlan/killingfloor-map-viewer). Склонируй его
рядом с этим репозиторием либо укажи `KF_ROM_JS` на его `kfrom.js`.

```bash
cd scripts
node bspstat.js       <Half-Life>/cstrike/maps/de_dust.bsp
node umodel-trailer.js <KillingFloor>/Maps      # каталог или файл
node romstat.js       <map.rom>
node meshbbox.js      <map.rom>
```
